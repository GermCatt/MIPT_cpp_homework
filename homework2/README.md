# ФизКат

Небольшая консольная программа для учёта парка прокатного транспорта и всякого сопутствующего инвентаря: велосипедов, электросамокатов, шлемов, док-станций и так далее.

Это второе ДЗ по C++. В нём тренируем ООП, в том числе множественное наследование, виртуальные методы, перегрузку операторов, шаблоны, исключения и умные указатели.

> **Проект пока в работе.** Сейчас есть основа иерархии объектов и тестовый `main()`. Учёт самого парка и консольные команды ещё предстоит написать.

## Как запустить

Пока всё лежит в одном `main.cpp`. Нужен C++20, потому что в коде используется `std::format`.

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic main.cpp -o fizkat
./fizkat
```

Для `std::format` также нужна достаточно новая стандартная библиотека (например, GCC 13+). Если собирать в VS Code, в `.vscode/tasks.json` нужно добавить аргумент `"-std=c++20"`. Для подсветки кода можно отдельно указать `"cppStandard": "c++20"`.

Сейчас `main()` просто проверяет, как работает электросамокат. Интерактивного ввода пока нет.

## Как устроены классы

```text
Item (абстрактный базовый класс инвентаря)
└── Transport (абстрактный класс транспорта)
    ├── Bike
    └── Scooter ─────────┐
                        │ множественное наследование
EnergyConsumer ─────────┘ (абстрактный класс потребителя энергии)
```

Следом планируется добавить `ElectricBike`, `Helmet`, `Dock` и ещё один собственный вид инвентаря для творческой части.

- `Item` — общий предок всего, что стоит на балансе. Хранит ID и имя, а ещё задаёт общий интерфейс для вывода, энергопотребления, отбора техники для новичков и техосмотра. `Describe()` — чисто виртуальный метод.
- `Transport` добавляет `noviceScore` — простоту управления от 1 до 10. Если оценка неправильная, конструктор бросает исключение. Для новичков подходит транспорт с оценкой от 6. Класс остаётся абстрактным благодаря `TransportType()`.
- `Bike` — обычный велосипед. Никакой электрической энергии не тратит, поэтому спокойно наследует `Item::DailyEnergy()` с результатом `0.0`.
- `EnergyConsumer` хранит расход энергии и умеет считать потребление и стоимость за несколько дней. Его `DailyEnergy()` — чисто виртуальный.
- `Scooter` — электросамокат. Он наследуется сразу от `Transport` и `EnergyConsumer`, а его `DailyEnergy()` переопределяет одноимённые методы обоих родителей.

Благодаря виртуальным методам можно будет обходить парк через указатели на `Item`, не перебирая типы с помощью `dynamic_cast`.

## Вывод информации и творческая часть

Для обычного списка перегружен `operator<<`. Он вызывает виртуальный `Describe()` и печатает короткую строку вроде `S-1 ModelX`.

А если хочется подробностей, есть `Details(days, tariff)`. Общую информацию собирает `Transport`, а виртуальный `ExtraDetails()` позволяет конкретному виду транспорта дописать что-то своё. Например, для электросамоката:

- `Details()` показывает в том числе суточное энергопотребление;
- `Details(30, 7.0)` ещё считает расход за 30 дней и стоимость при тарифе 7 руб./кВт·ч.

В дальнейшем для этого появится команда `details`: это будет дополнительная операция из творческой части. Ещё по заданию нужно придумать собственный вид транспорта или вещи — до него пока не дошли.

## Исключения

Пока есть два класса:

- `FleetError : std::runtime_error` — общий базовый класс ошибок;
- `InvalidArgumentError : FleetError` — некорректная оценка простоты, расход энергии, количество дней или тариф.

Позже добавится `InspectionRejectedError` для отказа техосмотра. Ошибки будет ловить обработчик команд: вывод `error: ...` останется в `catch`, а не внутри классов.

Проверку пустых и повторяющихся ID, как и полноценный разбор команд, ещё нужно дописать.

## Умные указатели (пока план)

Здесь будем использовать уточнённую версию требований преподавателя:

1. `unique_ptr` владеет новой техникой до техосмотра. Если проверка не пройдена, объект автоматически уничтожается, а парк не меняется.
2. После успешного техосмотра техника попадает в парк, где хранится как `std::shared_ptr<Item>`.
3. `weak_ptr` нужен для команды `focus`: «витрина» показывает выбранную позицию, но не становится её владельцем. После удаления объекта `show_focus` должен вывести `removed` или `expired`.

Сам `Fleet`, `ServiceCenter` и операции с умными указателями пока не написаны.

## Что с шаблонами и операторами

- `operator<<` уже работает.
- `operator<` ещё нужен для сортировки по инвентарному номеру. Кроме него, по заданию понадобится ещё одна перегрузка оператора.
- Шаблонный класс тоже впереди (один из вариантов — `Registry<T>`). Важно, чтобы он действительно использовался в программе.

## Какие команды должны работать

```text
add scooter id name energy score
add bike id name score
add ebike id name energy score
add helmet id name
add dock id name energy
energy
novice
list
focus id
show_focus
remove id
quit
```

Кроме них, нужно добавить команду для нового вида инвентаря и дополнительную операцию — скорее всего, `details`.

Транспорт перед добавлением проходит техосмотр. По учебному правилу, если в имени встречается `broken` (без учёта регистра), сервис отказывает, бросает `InspectionRejectedError`, а парк остаётся без изменений.
