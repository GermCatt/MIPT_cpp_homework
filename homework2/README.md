# Учёт городского транспорта

Небольшое консольное приложение на C++ для учёта транспорта и оборудования городского проката. Программа позволяет добавлять объекты в парк, удалять их по ID, просматривать списки, считать энергопотребление и выбирать объект для подробного просмотра.

Проект написан на C++20 и разделён на заголовки `.hpp` и файлы реализации `.cpp`. Сборка описана в `CMakeLists.txt`.

## Что умеет программа

- Добавлять велосипеды, электровелосипеды и электросамокаты.
- Добавлять оборудование: шлемы, налокотники и док-станции.
- Проверять транспорт при добавлении. Если в названии есть `broken` (регистр не важен), техосмотр не пройден и объект в парк не попадает.
- Не допускать пустые и повторяющиеся ID.
- Показывать весь парк с сортировкой по ID.
- Формировать список транспорта, подходящего новичкам. Сортировка — сначала по типу, затем по ID.
- Считать суммарное суточное энергопотребление. В расчёт входят все объекты, реализующие интерфейс `EnergyConsumer`, в том числе док-станции.
- Выбирать объект на витрину и просматривать его краткое или подробное описание.
- Рассчитывать потребление за заданное количество дней и стоимость энергии по заданному тарифу.

## Типы объектов

- `Bike` — обычный велосипед.
- `ElectricBike` — электровелосипед с суточным энергопотреблением.
- `Scooter` — электросамокат с суточным энергопотреблением.
- `Helmet` — шлем с размером `S`, `M`, `L` или `XL`.
- `ElbowPads` — налокотники.
- `DocStation` — док-станция с энергопотреблением и указанием района.

У шаблонов компилятор должен видеть реализацию при подстановке конкретного типа. Поэтому весь `BoundedValue<T>` и шаблонный `Commands::Add` остались в заголовках. Там же остался `Item::operator<=>` с выводимым типом `auto`: вызывающему коду нужно видеть тело для определения типа результата. Шаблонная функция `ReadNumber<T>` определена в `Console.cpp`: все её вызовы находятся в этом же файле и видят её реализацию. Безымянный `namespace` делает её внутренней вспомогательной функцией файла.

## Как устроен код

Основные классы разделены по ответственности:

- **`Item`** — общий абстрактный базовый класс инвентарного объекта: хранит ID и имя, задаёт интерфейс описания, типа и дополнительных признаков.
- **`Transport`** и **`Equipment`** — базовые классы для транспорта и оборудования.
- **`EnergyConsumer`** — отдельный интерфейс для объектов, потребляющих энергию. Его реализуют электрический транспорт и док-станция. Общий конструктор ограничивает суточный расход одной единицы диапазоном от 0 до 10000 кВт·ч включительно через `BoundedValue<double>`.
- **`ElectricTransport`** — общая реализация электрического транспорта.
- **`BoundedValue<T>`** — шаблонный класс для хранения значения с проверкой допустимого диапазона. Используется, например, для оценки пригодности новичкам и энергопотребления.
- **`Registry`** — хранит принятые объекты парка в `vector<shared_ptr<Item>>`, проверяет ID, ищет и удаляет объекты.
- **`ServiceCenter`** — проводит техосмотр.
- **`Fleet`** — управляет парком: добавляет и удаляет объекты, формирует списки, считает энергопотребление и управляет витриной.
- **`Commands`** — выполняет операции над парком, выводит результаты и обрабатывает ошибки операций. Строки ввода не разбирает.
- **`Console`** — читает строки целиком через `std::getline` в `Run()`, разбирает их через `std::istringstream` и вызывает методы `Commands`. `ParseCommand()` сопоставляет имя команды со значением `enum class Command`, затем `ExecuteCommand()` выбирает действие через `switch`. Неизвестное имя вызывает `InvalidArgumentError`. Разбор `add` и `details` вынесен в отдельные методы. `Execute()` ловит ошибки ввода и позволяет читать следующие команды.
- **`main()`** — настраивает консоль, создаёт `Console console` и вызывает `console.Run()`. Блоков `try/catch` в `main` нет.

### Схема наследования

Ветки дерева идут от базового класса к наследникам. Стрелки справа показывают второй базовый класс: `ElectricTransport` и `DocStation` используют множественное наследование. Все связи наследования — `public`; виртуального наследования здесь нет.

```text
Item (abstract)
|
+-- Transport (abstract)
|   |
|   +-- Bike
|   |
|   `-- ElectricTransport (abstract) <--- EnergyConsumer (abstract)
|       |
|       +-- Scooter
|       `-- ElectricBike
|
`-- Equipment (abstract)
    |
    +-- Helmet
    +-- ElbowPads
    `-- DocStation <-------------------- EnergyConsumer (abstract)
```

### Что находится за указателем на Item

Парк хранит `shared_ptr<Item>`, но за каждым указателем остаётся целый объект конкретного типа. Например, после `add scooter S-1 ModelX 2.5 8` структура объекта выглядит так:

```text
+----------------------------------------------------------------------+
| OBJECT: Scooter / ID: S-1 / NAME: ModelX                             |
+----------------------------------------------------------------------+
|                                                                      |
| Scooter                                                              |
| |  TypeName() -> "Электросамокат"                                    |
| |                                                                    |
| `-- ElectricTransport                                                |
|     |  DailyEnergy() -> 2.5                                          |
|     |                                                                |
|     +-- Transport                                                    |
|     |   |  noviceScore_ : BoundedValue<int>    = 8                   |
|     |   |                                                            |
|     |   `-- Item                                                     |
|     |       id_   : string                    = "S-1"                |
|     |       name_ : string                    = "ModelX"             |
|     |       GetId(), GetName(), Describe(), Details(), ...           |
|     |                                                                |
|     `-- EnergyConsumer                                               |
|         energy_ : BoundedValue<double>        = 2.5                  |
|                                                                      |
+----------------------------------------------------------------------+
```

Поля `id_` и `name_` находятся в `Item`, `noviceScore_` — в `Transport`, а `energy_` — в `EnergyConsumer`. Вызовы через `Item` используют виртуальные методы конкретного объекта; доступ к энергетическому интерфейсу получается через `dynamic_cast<const EnergyConsumer*>`.

У `Describe()`, `GetId()` и `GetName()` в `Item` реализован костыль, чтобы они соответствовали условию: они объявлены с `= 0`, но их тела написаны отдельно, за классом. Поэтому функции остаются чисто виртуальными. `Transport` и `Equipment` переопределяют их и явно вызывают `Item::Describe()`, `Item::GetId()` и `Item::GetName()`. Общая реализация живёт в одном месте, поля остаются закрытыми, а требования задания соблюдены.

### Что находится внутри Fleet

Пример парка из четырёх объектов после `focus S-1`. Стрелки `shared` обозначают владение; пунктир от `focus_` ведёт к тому же самокату, а не к его копии.

```text
+----------------------------------------------------------------------+
| Fleet                                                                |
+----------------------------------------------------------------------+
|                                                                      |
| registry_ : Registry                                                 |
| |                                                                    |
| `-- items_ : vector<shared_ptr<Item>>                                |
|     |                                                                |
|     +-- [0] ---- shared ----> Scooter "S-1" <-------.                |
|     +-- [1] ---- shared ----> Bike "B-1"            :                |
|     +-- [2] ---- shared ----> Helmet "H-1"          :                |
|     `-- [3] ---- shared ----> DocStation "D-1"      :                |
|                                                     :                |
| focus_ : weak_ptr<Item> - - - - - - - - - - - - - - :                |
|                                                                      |
| focusWasSet_ : bool = true                                           |
|                                                                      |
| serviceCenter_ : ServiceCenter                                       |
| `-- Inspect(const Item&)                                             |
|                                                                      |
+----------------------------------------------------------------------+
```

Объекты справа создаются отдельно в динамической памяти; вектор хранит указатели на них. После `remove S-1` в обычном сценарии команд последний владеющий указатель на самокат исчезает, объект уничтожается, а `focus_` становится `expired`. Флаг `focusWasSet_` остаётся `true`, поэтому программа различает «витрину ещё не выбирали» и «выбранный объект удалён».

### Владение объектами

При добавлении объект сначала передаётся в `Fleet` через `unique_ptr`. Если техосмотр или проверка добавления завершается исключением, временный объект автоматически уничтожается.

После успешных проверок объект хранится в `Registry` через `shared_ptr`. Витрина использует `weak_ptr`: она наблюдает за выбранным объектом, но не продлевает срок его жизни. Поэтому после удаления объекта из парка витрина становится `expired`.

### Исключения

Все свои исключения наследуются от `FleetError`, а он — от `std::runtime_error`. Типы объявлены в `src/common/Errors.hpp` и используются в соответствующих классах. Обработчики в `Console` и `Commands` передают сообщения общему модулю `ConsoleOutput`.

| Исключение | Когда возникает |
| --- | --- |
| `InvalidArgumentError` | Неверный синтаксис или неизвестная команда/тип; пустой, повторяющийся или ненайденный ID; нулевой указатель; оценка вне 1..10; суточная энергия вне 0..10000 кВт·ч или неконечное значение; неверный размер шлема; запрос энергетического расчёта для обычной вещи. Также используется в общей проверке `BoundedValue<T>` и при делении на ноль. |
| `InspectionRejectedError` | Техосмотр обнаружил `broken` в имени транспорта без учёта регистра. |
| `EmptyRegistryError` | Операция требует содержимого парка, а парк пуст: например `list`, `novice` или `energy`. |
| `NoEnergyConsumers` | Парк непустой, но ни один объект не реализует `EnergyConsumer`. |
| `NoNoviceTransport` | Парк непустой, но подходящего новичкам транспорта нет. |
| `EnergyCalculationError` | Период вне 0..365 дней, тариф вне 0..9999 руб./кВт·ч либо переполнение при расчёте энергии или стоимости. Неконечный тариф тоже недопустим. |

Ошибки возникают через `throw`; из `catch` вызывается `ConsoleOutput::Error(e.what())`. Все тексты исключений написаны на русском, начинаются с заглавной буквы и заканчиваются точкой. Префикс `error:` сохранён из условия задания. Например:

```text
error: Неверный формат команды.
error: Суточное потребление должно быть от 0 до 10000 кВт·ч.
error: Объект с ID "S-1" не найден.
```

В терминале ошибки и ответ `already removed` выделяются красным, после сообщения цвет сбрасывается. При перенаправлении вывода в файл или канал управляющие последовательности цвета не добавляются. Цвет также отключается при непустой переменной окружения `NO_COLOR` или `TERM=dumb`. В Windows, если режим обработки ANSI включить не удалось, ошибки выводятся обычным текстом. Сообщения и результаты команд выводятся в стандартный поток вывода.

Обычные состояния показываются через `ConsoleOutput::Message()` без красного цвета и префикса ошибки: «Парк пуст.», «Нет транспорта, подходящего для новичков.», «Витрина ещё не установлена.». Для удалённой позиции витрины выводится ответ `already removed`; он выводится красным через `ConsoleOutput::Removed()` без префикса ошибки. При `energy` после пояснения о пустом парке или отсутствии потребителей по-прежнему выводится `0.0 кВт·ч` отдельной строкой.

Если `remove ID` или `focus ID` не находит объект, даже в пустом парке, выводится `error: Объект с ID "..." не найден.`. Неудачный `focus ID` сохраняет прежнее состояние витрины. В `EnergyDetails()` ошибка диапазона от `BoundedValue<T>` переводится в `EnergyCalculationError`. Если число нельзя разобрать целиком, это ошибка синтаксиса команды.

### Перегрузка операторов

- `operator<<` печатает ID и имя через виртуальный `Describe()`, поэтому работает для всех видов инвентаря.
- `Item::operator<=>` сравнивает позиции по ID. В C++20 выражения `<`, `>`, `<=` и `>=` могут использовать этот оператор. В частности, `list` сортирует позиции через `<`. Отдельного тела `operator<` нет: здесь я использовал возможность C++20.
- Дополнительное сравнение позиций по ID реализовано тем же `<=>`. Он возвращает результат трёхстороннего сравнения; автоматического `operator==` у `Item` при такой записи нет.
- У `BoundedValue<T>` есть сравнения и арифметические операторы. Умножение реально используется в расчёте энергии и стоимости, деление проверяет нулевой делитель.

### Шаблоны

`BoundedValue<T>` используется для `int` и `double`: проверяет оценку новичка, суточный расход, дни и тариф. Одна реализация проверки диапазона работает для разных числовых типов. `Commands::Add<T, Args...>` создаёт разные виды объектов через `make_unique` и передаёт аргументы с `std::forward`, чтобы не копировать одинаковую логику добавления для каждого типа.

`ReadNumber<T>` в [src/console/Console.cpp](src/console/Console.cpp) используется для чтения числовых аргументов типа `int` и `double`. Сначала он выделяет один аргумент как строку, затем разбирает его отдельным потоком. Условие `!(number >> value) || !number.eof()` отклоняет неудачное преобразование или непрочитанный остаток: например. Пробелы между аргументами и в конце команды в эту строку не попадают. Проверка числовой записи выполняется здесь, а допустимых диапазонов — в доменной модели.

## Творческая часть и отличия формата

Добавлен свой тип `ElbowPads` с командой `add elbowpads`. Команда `details` показывает подробности выбранного объекта; для потребителей энергии она также умеет считать расход за период и стоимость. Шлем получил размер, док-станция — район.

Поэтому в рамках творческой части формат из примера задания расширен намеренно: `add helmet` обязательно принимает размер, а `add dock` — район. Короткие команды `add helmet H-1 Pro` и `add dock D-1 Hub 10.0` не поддерживаются. Нужны, например, `add helmet H-1 Pro M` и `add dock D-1 Hub 10.0 North`. Значения по умолчанию не подставляются.

Вывод `energy` тоже уточнён: к числу добавлена единица `кВт·ч`. У команды три разных случая с нулевым расходом: пустой парк, парк без потребителей энергии и парк с потребителями, чей расход равен нулю. Во всех трёх случаях выводится `0.0 кВт·ч`; в первых двух перед числом отдельной строкой печатается пояснение. Количество объектов выводит отдельная команда `count`, суммарную энергию — `energy`.

## Команды

Команды вводятся по одной на строку. Пустые строки игнорируются. Аргументы разделяются пробелами или табуляцией; несколько пробелов подряд, пробелы в начале и конце строки допустимы. Имена команд и типов вводятся в нижнем регистре. ID, имя объекта и район — по одному слову; кавычки для объединения слов не поддерживаются.

Числовые аргументы проверяются целиком. Энергия и тариф читаются как `double`: допустимы `7`, `7.0`, `7.5` и `7e1`; десятичный разделитель — точка. Целая запись `7` сразу читается как значение `7.0`, поэтому дописывать `.0` не требуется. Дни и оценка новичка читаются как `int`.

Например, `details 30 7` и `details 30 0.5` корректны, а `details 30.5`, `details 30+0.5` и `add scooter S-1 City 2.5+8` вызывают ошибку синтаксиса. Недостающие обязательные и лишние аргументы тоже считаются ошибкой: `details 30` и `energy extra` не выполняются. После сообщения об ошибке программа читает следующую команду. Аргументы с новой строки не дочитываются к предыдущей.

### Добавление объектов

```text
add bike B-1 City 8
add ebike E-1 Trek 3.0 9
add scooter S-1 ModelX 2.5 8
add helmet H-1 Pro M
add dock D-1 Hub 10 North
add elbowpads P-1 Pro
```

У каждого типа свой набор аргументов:

- `bike`: ID, имя, оценка пригодности новичкам.
- `ebike`: ID, имя, суточное энергопотребление, оценка пригодности новичкам.
- `scooter`: ID, имя, суточное энергопотребление, оценка пригодности новичкам.
- `helmet`: ID, имя, размер.
- `dock`: ID, имя, суточное энергопотребление, район.
- `elbowpads`: ID, имя.

Суточное энергопотребление для `scooter`, `ebike` и `dock` должно быть от `0` до `10000` кВт·ч включительно. Например, `10000` и `1e4` допустимы, а `10000.1` и `1e5` отклоняются. Лимит задан константой `maxDailyEnergy_` в `EnergyConsumer` и передаётся в `BoundedValue<double>` при создании объекта. Он относится к каждой единице отдельно; суммарная энергия парка может превышать 10000 кВт·ч.

Успешный `add` ничего не печатает. Результат можно проверить командами `list` или `count`.

### Остальные команды

- `remove S-1` — удалить объект по ID.
- `remove` — удалить живой объект, выбранный на витрину; ID берётся из текущего фокуса.
- `list` — показать весь парк.
- `novice` — показать транспорт, подходящий новичкам.
- `energy` — показать суммарное суточное энергопотребление с одним знаком после точки и единицей `кВт·ч`. Если парк пуст, выводится «Парк пуст.»; если в нём нет потребителей энергии — «В парке нет потребителей энергии.». После любого из этих пояснений на следующей строке выводится `0.0 кВт·ч`. Если потребители есть, но их суммарное потребление равно нулю, выводится только `0.0 кВт·ч`.
- `count` — вывести количество объектов на балансе одним числом; для пустого парка — `0`.
- `focus S-1` — установить объект на витрину. ID обязателен: `focus` без аргумента считается ошибкой синтаксиса.
- `show_focus` — показать краткое описание объекта на витрине.
- `details` — показать подробную информацию об объекте на витрине.
- `details 30 7.5` — запросить подробную информацию с расчётом энергопотребления за 30 дней по тарифу 7.5.
- `quit` — завершить программу. Конец входного потока (EOF) также завершает чтение команд. У `quit` нет аргументов: `quit extra` выдаёт ошибку и оставляет программу работающей.

После успешного удаления через `remove ID` или `remove` выводится `Объект удалён`. У `remove` без ID сначала проверяется витрина. Если фокус ещё не выбран, выводится «Витрина ещё не установлена.». Если выбранный объект уже удалён, выводится `already removed`; парк не меняется. Повторное добавление объекта с тем же ID не оживляет старую витрину: для нового объекта нужен новый `focus ID`. Явный `remove ID` работает независимо от состояния витрины.

```text
add bike B-1 City 8
focus B-1
remove
show_focus
remove
```

Первый `remove` удалит велосипед и выведет `Объект удалён`. `show_focus` и повторный `remove` выведут `already removed`.

У команды `details` два режима:

- **Без аргументов (`details`)** — выводится подробное описание объекта на витрине. Для потребителей энергии также показывается суточное потребление, без расчёта за период и стоимости.
- **С аргументами (`details <дни> <тариф>`)** — команда предназначена только для объектов, реализующих `EnergyConsumer`. Для такого объекта выводится обычное подробное описание и дополнительно рассчитываются суточное потребление, потребление за указанный период и стоимость энергии.
- **Если на витрине объект не реализует `EnergyConsumer`**, вызов `details` с аргументами завершается ошибкой. Обычное описание объекта при этом не выводится.

Для расчёта допустимы целые дни от `0` до `365` включительно (год принят равным 365 дням) и тариф от `0` до `9999` рублей за кВт·ч включительно. Выход за границы или переполнение вызывает `EnergyCalculationError`; неполный расчёт не печатается. Проверки конечности результатов сохранены на случай изменения лимитов или реализации `DailyEnergy()` у новых наследников.

Например, `details 30 7.5` на электросамокате покажет его описание и энергетический расчёт за 30 дней. Та же команда на шлеме или обычном велосипеде выдаст ошибку, потому что эти объекты не потребляют энергию.

## Сборка через CMake

Нужны CMake 3.20 или новее, Ninja и компилятор C++20 со стандартной библиотекой, поддерживающей `std::format`.

### Первый запуск в Windows PowerShell

```powershell
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_CXX_COMPILER=g++
cmake --build build
.\build\fleet.exe
```

### Первый запуск в Linux

```bash
cmake -S . -B build -G Ninja \
  -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_COMPILER=g++

cmake --build build
./build/fleet
```

### Что записано в CMakeLists.txt

- `project(FizKat LANGUAGES CXX)` задаёт имя проекта и язык C++.
- `add_executable(fleet ...)` перечисляет исходники одной исполняемой программы `fleet` с путями внутри `src`.
- `target_include_directories(fleet PRIVATE "${CMAKE_CURRENT_SOURCE_DIR}/src")` добавляет `src` в путь поиска заголовков для этой программы.
- `CXX_STANDARD 20` и `CXX_STANDARD_REQUIRED YES` требуют C++20; `CXX_EXTENSIONS NO` отключает расширения стандарта компилятора.
- `target_compile_options` включает предупреждения. Для MSVC также задан `/utf-8`.

Официальная справка: [команды настройки и сборки CMake](https://cmake.org/cmake/help/latest/manual/cmake.1.html), [генератор Ninja](https://cmake.org/cmake/help/latest/generator/Ninja.html).
